# PHASE 2 — ภาษีและการเงินครบชุด

### M10 — รายงาน VAT
- รายงานภาษีขาย / ภาษีซื้อ รายเดือน ตามรูปแบบที่กรมสรรพากรกำหนด (ลำดับ, วันที่, เลขที่ใบกำกับ, ชื่อผู้ซื้อ/ผู้ขาย, เลขผู้เสียภาษี, สาขา, มูลค่า, VAT)
- สรุปยอดสำหรับ ภ.พ.30: ภาษีขาย − ภาษีซื้อ = ต้องชำระ / ขอคืน / ยกไป
- รองรับภาษีซื้อที่ขอคืนไม่ได้ (ตั้งเป็นค่าใช้จ่าย) และภาษีซื้อที่ยื่นเลื่อนเดือน (ภายในระยะเวลาที่กฎหมายกำหนด)
- Export PDF + Excel

### M11 — รายงานภาษีหัก ณ ที่จ่าย
- สรุป ภ.ง.ด.3 (บุคคลธรรมดา) / ภ.ง.ด.53 (นิติบุคคล) รายเดือน แยกตามประเภทเงินได้
- ทะเบียน 50 ทวิ ที่ออกแล้ว + ทะเบียน 50 ทวิ ที่ได้รับ (ภาษีถูกหัก)
- Export PDF + Excel (และไฟล์ข้อความสำหรับนำเข้าระบบยื่นออนไลน์ ถ้ารูปแบบชัดเจน; ถ้าไม่แน่ใจให้ถามก่อน)

### M12 — กระทบยอดธนาคาร
- นำเข้า bank statement (CSV/Excel) พร้อมหน้า map คอลัมน์ และจำ mapping ต่อธนาคาร
- จับคู่อัตโนมัติ (ยอดเงิน + วันที่ใกล้เคียง + ข้อความอ้างอิง) แล้วให้ผู้ใช้ยืนยัน
- รายการที่ไม่มีคู่ → สร้างเอกสารใหม่จากรายการนั้นได้ (เช่น ค่าธรรมเนียมธนาคาร, ดอกเบี้ย)
- รายงานกระทบยอด: ยอดตาม statement vs ยอดตามบัญชี + รายการค้าง

### M13 — สต็อกสินค้า
- สินค้าแบบนับสต็อก / ไม่นับสต็อก, คลังสินค้า (เริ่ม 1 คลัง แต่ data model รองรับหลายคลัง)
- รับเข้าจากเอกสารซื้อ, ตัดออกจากเอกสารขายอัตโนมัติ, ปรับปรุงสต็อก (นับจริง/เสียหาย)
- ต้นทุนแบบ FIFO หรือถัวเฉลี่ยถ่วงน้ำหนัก (เลือกต่อบริษัท ตั้งครั้งเดียว) และลงบัญชีต้นทุนขายอัตโนมัติ
- รายงาน: สินค้าคงเหลือ, ความเคลื่อนไหว, รายงานสินค้าและวัตถุดิบตามแบบสรรพากร, แจ้งเตือนสต็อกต่ำ

### M14 — สินทรัพย์ถาวร
- ทะเบียนสินทรัพย์ (สร้างจากเอกสารซื้อได้), ประเภท, อายุการใช้งาน, มูลค่าซาก
- ค่าเสื่อมราคาแบบเส้นตรง คำนวณรายเดือน และลงบัญชีอัตโนมัติด้วยปุ่มเดียวต่อเดือน
- ขาย/ตัดจำหน่ายสินทรัพย์ → คำนวณกำไร/ขาดทุนจากการจำหน่าย

### M15 — ปิดงวดบัญชี
- ล็อกงวดรายเดือน: หลังล็อกห้าม post/void เอกสารในงวดนั้น (เฉพาะ owner ปลดล็อกได้ และต้องบันทึก audit log)
- Checklist ก่อนปิดงวด: เอกสารร่างค้าง, statement ที่ยังไม่กระทบยอด, ค่าเสื่อมเดือนนั้น
- ปิดปีบัญชี: โอนกำไร/ขาดทุนสุทธิเข้ากำไรสะสม, ยอดยกไปปีใหม่

### M16 — Dashboard การเงินฉบับเต็ม
- รายได้ ค่าใช้จ่าย กำไร กระแสเงินสด แนวโน้ม 12 เดือน
- ลูกหนี้/เจ้าหนี้ตามอายุ (aging 0–30 / 31–60 / 61–90 / 90+)
- กำหนดภาษีที่ต้องยื่นเดือนนี้ (VAT, ภ.ง.ด.) พร้อมยอดประมาณการ
- ดูรายบริษัท หรือรวมทุกบริษัทที่เป็นสมาชิก

# PHASE 3 — OCR Automation

## หลักการ
- **OCR ไม่ลงบัญชีเองเด็ดขาด** ผลลัพธ์ทุกอย่างจะกลายเป็น "เอกสารร่าง" (`status = draft`, `source = ocr`) ให้คนยืนยันก่อน post
- โปรแกรม OCR ของเจ้าของระบบเป็นของภายนอก แอปเชื่อมผ่าน **JSON contract** เท่านั้น ห้ามผูกกับโค้ดภายในของ OCR
- เก็บไฟล์ต้นฉบับทุกไฟล์ไว้เป็นไฟล์แนบของเอกสารเสมอ

## ⚠️ ข้อมูลที่เจ้าของต้องกรอกก่อนเริ่ม M17 (Claude Code ต้องถามถ้ายังว่าง)
- [ ] โปรแกรม OCR รันที่ไหน: เครื่อง local / server / cloud function
- [ ] เรียกใช้อย่างไร: CLI, HTTP API, หรืออ่าน/เขียนไฟล์ในโฟลเดอร์
- [ ] ตัวอย่าง JSON output จริง 3–5 ไฟล์ (ใบกำกับภาษี, ใบเสร็จ, บิลเงินสด) วางไว้ที่ `samples/ocr/`
- [ ] มี confidence score ต่อ field หรือไม่

### M17 — JSON Contract + Ingestion API
- เขียน JSON Schema `ocr-document.v1.json` จากตัวอย่างจริง ครอบคลุมอย่างน้อย:
  `document_type`, `document_number`, `issue_date`, `seller{name, tax_id, branch, address}`, `buyer{...}`, `lines[{description, qty, unit_price, amount}]`, `subtotal`, `discount`, `vat_rate`, `vat_amount`, `wht_rate`, `wht_amount`, `total`, `currency`, `confidence{field: 0–1}`, `source_file`
- ตารางใหม่: `ocr_jobs` (file, status: queued / processing / done / failed / needs_review, raw_json, error, company_id, created_by)
- ช่องทางรับผล OCR: endpoint (Supabase Edge Function) ที่รับ JSON + ตรวจ schema + ตรวจ API key ต่อบริษัท
- เก็บ `raw_json` ต้นฉบับไว้เสมอ เพื่อ debug และปรับปรุงความแม่นยำ

### M18 — ช่องทางนำเข้าไฟล์
- **เว็บ:** ลากวาง PDF/รูปได้หลายไฟล์พร้อมกัน
- **มือถือ:** ถ่ายรูปบิล (Capacitor Camera), เลือกจากอัลบั้ม, รับไฟล์จากเมนูแชร์ของระบบ (share sheet)
- **โฟลเดอร์ในเครื่อง:** desktop agent ตัวเล็ก (Node script หรือใช้ Power Automate Desktop) เฝ้าโฟลเดอร์ที่กำหนด → ส่งไฟล์ใหม่ขึ้นระบบ → ย้ายไฟล์ที่ส่งแล้วไปโฟลเดอร์ `processed/` (ห้ามลบไฟล์ของผู้ใช้)
- ทุกช่องทางสร้าง `ocr_jobs` แบบเดียวกัน แล้วส่งให้ OCR ตามวิธีที่ระบุไว้ในข้อมูลที่ต้องกรอก

### M19 — Validation + แปลงเป็นเอกสารร่าง
- ตรวจอัตโนมัติ:
  - ผลรวมรายการ − ส่วนลด + VAT = ยอดรวม (ยอมให้คลาดเคลื่อนจากการปัดเศษ ±0.01 ต่อบรรทัด)
  - VAT = ฐานภาษี × อัตรา
  - เลขผู้เสียภาษี 13 หลัก ผ่าน checksum
  - วันที่ไม่อยู่ในอนาคต และไม่อยู่ในงวดที่ล็อกแล้ว
  - **เอกสารซ้ำ:** เลขผู้เสียภาษีผู้ขาย + เลขที่เอกสาร + ยอดรวม ตรงกับที่มีอยู่แล้ว
- จับคู่ผู้ขายจากเลขผู้เสียภาษี; ถ้าไม่เจอ → เสนอสร้างผู้ติดต่อใหม่จากข้อมูล OCR
- สร้างเอกสารร่าง (ค่าใช้จ่าย/ซื้อ หรือขาย ตาม `document_type`) พร้อมแนบไฟล์ต้นฉบับ

### M20 — คิวตรวจทาน (Review Queue)
- หน้ารวมเอกสารรอตรวจ: เรียงตาม ปัญหามาก → น้อย
- หน้าจอแบ่งครึ่ง: ภาพเอกสารต้นฉบับ | ฟอร์มที่กรอกให้แล้ว
- Field ที่ confidence ต่ำกว่า threshold (ค่าเริ่มต้น 0.85 ตั้งค่าได้) หรือไม่ผ่าน validation → ไฮไลต์สี + บอกเหตุผล
- ปุ่ม "ยืนยันและบันทึก" (post) / "บันทึกเป็นร่าง" / "ปฏิเสธ"
- ใช้งานบนมือถือได้ (เลื่อนดูภาพ/ฟอร์มสลับกัน)

### M21 — ระบบเรียนรู้จากการแก้ไข
- เก็บทุกการแก้ไขของผู้ใช้ (ค่าที่ OCR อ่านได้ → ค่าที่ผู้ใช้แก้) ลงตาราง `ocr_corrections`
- กฎต่อผู้ขาย (`vendor_rules`): ผู้ขายรายเดิม → เติมบัญชีค่าใช้จ่าย, หมวด, VAT mode, % หัก ณ ที่จ่าย ให้อัตโนมัติ
- ผู้ใช้ดูและแก้กฎได้เอง
- Export ข้อมูลการแก้ไขเป็น JSON เพื่อนำไปปรับปรุงโปรแกรม OCR

### M22 — Auto-post (ตัวเลือก ปิดไว้เป็นค่าเริ่มต้น) + รายงานความแม่นยำ
- เปิดให้ post อัตโนมัติได้เฉพาะเมื่อ: ผู้ขายมี vendor rule แล้ว + ทุก field ผ่าน validation + confidence ≥ threshold ที่ตั้งไว้ (เช่น 0.97)
- เอกสารที่ auto-post ต้องติดป้าย "Auto" และ void ได้ตามปกติ
- รายงานความแม่นยำ: % field ถูกต้องตาม field / ผู้ขาย / ประเภทเอกสาร, เวลาเฉลี่ยตั้งแต่อัปโหลดจนถึง post, จำนวนเอกสารซ้ำที่จับได้
- E2E: อัปโหลด PDF ตัวอย่าง → ได้ JSON → เอกสารร่าง → ตรวจทาน → post → อยู่ในรายงานภาษีซื้อของ M10 ถูกต้อง
